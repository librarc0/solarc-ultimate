## 算法设计前置说明

> 本章节为规范的技术背景，描述 OpenSkill 算法与飞盘比赛数据结合的方案以及模型选择依据。实现时依据此说明选型。

### OpenSkill 模型选择

`openskill` 库提供三种主要模型，各有适用场景：

| 模型 | 核心假设 | 适用场景 | 本项目适用性 |
|------|---------|---------|-------------|
| **PlackettLuce** | 每支队伍的表现强度决定排名概率，多队伍同时参与排名 | 多队伍混战、排名竞争 | ✅ **推荐选用**：飞盘内战可看作两支队伍的相对排名竞争，且支持非对称人数队伍 |
| **ThurstoneMosteller Full** | 每场比赛是两两对比，基于正态分布差值 | 纯 1v1 对决 | ⚠️ 适合1v1记分，但飞盘团队战效果次于 PlackettLuce |
| **BradleyTerry Full** | 两两对比，基于对数几率差值 | 1v1 或两队对战 | ⚠️ 对两队对战也可用，但处理非对称人数时需额外处理 |

**结论**：选用 **PlackettLuce** 模型，理由：
1. 天然支持两支队伍（A vs B）的相互排名，语义与飞盘比赛吻合
2. 支持任意人数的不对称队伍（7v6 常见）
3. 同一模型可无缝扩展到未来多队伍混战场景

### OpenSkill + 飞盘数据的结合方案

**OpenSkill 原生能力**：只接受「队伍分组」和「排名结果」，产出每位玩家更新后的 μ/σ。本身不理解进球/助攻。

**本项目扩展方案**（个人贡献加权）：

```
1. 基础更新（纯 OpenSkill）
   - 将两队队员按「每人独立一个虚拟评分」分组传入 PlackettLuce
   - 胜队排名=1，败队排名=2，算法输出 Δμ_base（每人基础 μ 变化）

2. 个人贡献分计算（Level 2/3 可用）
   - contribution = beta * goals + gamma * assists + d_weight * max(0, plus_minus)
   - 同队内按贡献分比例调整 Δμ：
     adjusted_Δμ = Δμ_base * (1 + alpha * (contribution_i / mean_contribution_team - 1))
   - alpha 控制个人贡献的调整幅度，≥0 且 ≤1
   - 保证：胜队队员不会因贡献低而变成负 Δμ（下限 = 0.1 * Δμ_base）

3. 保守评分更新
   - conservative_rating = μ - 3σ（OpenSkill 标准保守估计）

4. 综合排名分（可选，用于排行榜）
   - composite = ts_weight * conservative_rating + perf_weight * avg_performance_score
   - avg_performance_score = 最近 N 场 contribution_score 均值（归一化到 [0, 100]）
```

### 可输出的技术参数

每场比赛计算后系统可产出以下参数供查阅：

| 参数名 | 含义 | 用途 |
|-------|------|------|
| `mu` | 当前技能均值（Bayesian mean） | 核心评分，反映真实技术水平 |
| `sigma` | 技能不确定度 | σ 越小代表样本越充分，评分越可信 |
| `conservative_rating` | μ - 3σ，保守估计 | 用于排行榜排序（避免新手因不确定性被高估） |
| `delta_mu` | 本场比赛 μ 变化量 | 展示单场涨跌幅 |
| `delta_sigma` | 本场比赛 σ 变化量（通常为负，σ 收窄） | 反映数据积累程度 |
| `win_probability` | 与某对手的预期胜率（可按需计算） | 赛前阵容分析、平衡度评分 |
| `team_balance_score` | 两队 conservative_rating 均值差 | 帮助管理员调整阵容，越接近 0 越平衡 |
| `contribution_score` | 本场个人贡献分（beta*g + gamma*a + d） | 个人面板趋势图原始数据 |
| `performance_trend` | 最近 10 场 contribution_score 均值 | 个人能力走势 |
| `avg_goals_per_game` | 场均进球 | 雷达图进攻维度 |
| `avg_assists_per_game` | 场均助攻 | 雷达图助攻维度 |
| `avg_plus_minus_per_game` | 场均防守盘净值 | 雷达图防守维度 |
| `stability_index` | 1/σ 归一化，σ 越小稳定性越高 | 雷达图稳定性维度 |

### 默契度（Chemistry）算法设计

**目的**：量化两名队员在场上的配合度，作为排行榜的独立维度（默契度榜）。

**计算公式**：
```
chemistry(A, B) = chem_w1 * wins_together(A, B)
               + chem_w2 * combo_count(A, B)

其中：
- wins_together(A, B)  = A 和 B 作为同队且队伍获胜的场次数
- combo_count(A, B)    = A 作为得分者且 B 作为助攻者，或 B 作为得分者且 A 作为助攻者的总次数（顺序不限，双向累计）
- chem_w1, chem_w2     = 权重系数，来自 TeamSettings（默认 chem_w1=1.0, chem_w2=2.0）
```

**输出**：`chemistry_score(A, B)`，每对队员一个分值；排行榜（默契度榜）按此值降序显示配对列表。

**边界处理**：
- 两名队员同场次数 < 3 时，chemistry_score 标记为"数据不足"，不参与排行（避免小样本高估）
- chemistry 为对称关系：`chemistry(A, B) == chemistry(B, A)`，存储时以 `min(id_A, id_B)` 为主键避免重复

## 用户场景与测试 *(必填)*

### 用户故事 1 - 基础评分：内战更新所有队员 μ/σ (优先级: P1)

每场内战提交后，引擎自动用 PlackettLuce 更新参与者的 μ 和 σ，胜队 μ 上升、败队 μ 下降，所有参与者 σ 收窄。

**优先级原因**: 这是整个系统的核心价值，没有评分更新系统毫无意义。

**独立测试**: 单元测试：构造 A队(3人) vs B队(3人)、A队赢，调用引擎，断言所有 A队员 μ 增加、B队员 μ 减少、所有人 σ ≤ 初始值。

**验收场景**:

1. **给定** 一场内战数据（Level 1）已构造完毕，**当** 调用评分引擎，**那么** 返回每位参与者的更新后 μ 和 σ，胜队所有成员 `mu_after > mu_before`，败队所有成员 `mu_after < mu_before`。
2. **给定** 一场平局（比分相等），**当** 调用引擎，**那么** 双方 μ 变化极小（PlackettLuce 对平局有内建处理），σ 正常收窄。
3. **给定** 一位未参与本场比赛的队员，**当** 比赛提交后，**那么** 该队员的 μ/σ 不发生任何变化。

---

### 用户故事 2 - 个人贡献加权（Level 3 数据） (优先级: P1)

有个人统计数据时，同队队员根据个人表现获得不同幅度的 μ 调整——贡献大的涨幅更大，贡献小的涨幅更小（但不会因在胜队而反向扣分）。

**优先级原因**: 个人贡献加权是本系统相较纯团队评分的最大价值点，激励场上积极表现。

**独立测试**: 单元测试：A队胜利，player1有3个进球、player2有0个贡献，断言 `player1.delta_mu > player2.delta_mu`（两者均 > 0）。

**验收场景**:

1. **给定** data_level=3 的比赛，**当** 引擎计算时，**那么** 同队队员的 μ 变化量按个人贡献分比例调整：`contribution = beta * goals + gamma * assists + d_weight * max(0, plus_minus)`；贡献越高调整幅度越大，系数来自当前队伍配置。
2. **给定** 败队中有一名表现极好的队员（进球 5 个但队伍输了），**当** 引擎计算，**那么** 该队员 μ 下降幅度应小于同队其他贡献为零的队员（贡献加权在胜负两个方向均有效）。
3. **给定** 贡献分为 0 的队员，**当** 引擎计算，**那么** 该队员的 μ 变化 ≥ 基础 OpenSkill 变化的 10%（不额外惩罚，但不享受贡献加成）。

---

### 用户故事 3 - 外战对手建模（虚拟对手） (优先级: P1)

外战中没有对手队员数据，系统使用对手强度（1-10）映射为虚拟对手的 μ/σ，构造虚拟队伍参与 PlackettLuce 计算。

**优先级原因**: 外战评分必须合理，否则参与外战的队员评分与只打内战的队员不可比较。

**独立测试**: 对手强度=10 时虚拟对手 μ ≈ 50，对手强度=1 时虚拟对手 μ ≈ 15，击败强队的 μ 增量 > 击败弱队的 μ 增量。

**验收场景**:

1. **给定** 外战，对手强度=5（中等），本队赢，**当** 引擎计算，**那么** 本队 μ 小幅上升；相比之下，对手强度=9 且本队赢，本队 μ 大幅上升。
2. **给定** 对手强度参数，**当** 映射为虚拟对手 μ，**那么** 使用线性映射（强度1→μ≈15，强度10→μ≈50），虚拟对手 σ 固定为合理值（反映"较低不确定性"的中高水平对手）。
3. **给定** 外战中记录了本队个人统计，**当** 引擎计算，**那么** 个人贡献加权同样适用（Level 3 外战）。

---

### 用户故事 4 - 管理员配置算法系数 (优先级: P1)

管理员通过 API 修改本队的算法系数，修改后在下一场比赛提交时生效（不追溯历史比赛）。

**优先级原因**: 不同飞盘队伍风格不同（防守型 vs 进攻型），系数可调性是本项目核心差异化功能，也是章程约定（宪章 I 原则）。

**独立测试**: 修改 alpha 系数后提交一场新比赛，与修改前同类型比赛相比，队员 μ 变化幅度应有差异（可通过单元测试固定对比）。

**验收场景**:

1. **给定** 管理员已登录，**当** 调用算法系数修改接口（包含 alpha、beta、gamma 等参数），**那么** 队伍配置表更新，系统返回 200 和更新后的配置。
2. **给定** 非管理员用户，**当** 尝试修改算法系数，**那么** 系统返回 403。
3. **给定** 队伍尚未配置系数，**当** 引擎被调用，**那么** 引擎使用内置默认值正常运行，不报错。
4. **给定** 管理员设置了非法值（如 beta=3.0 超出合理范围），**当** 调用修改接口，**那么** 系统返回 422，说明每个参数的有效范围。

---

### 用户故事 5 - 输出多维度技术指标供查阅 (优先级: P2)

除了 μ/σ 之外，引擎计算后还应输出可供前端展示的多维度指标，用于个人能力雷达图和队伍平衡分析。

**优先级原因**: 多维度指标是产品体验的亮点，建立在基础评分正确的前提上，因此为 P2。

**独立测试**: 提交一场比赛后，个人信息接口应返回含 `conservative_rating`、`win_rate`、`contribution_score` 等字段；赛前平衡预览接口返回双队平均 conservative_rating 及差值。

**验收场景**:

1. **给定** 队员有 ≥ 5 场历史比赛，**当** 请求个人面板数据，**那么** 系统返回：`conservative_rating`（μ - 3σ）、`win_rate`、`avg_goals_per_game`、`avg_assists_per_game`、`avg_plus_minus`、`performance_trend`（最近 10 场贡献分均值）。
2. **给定** 内战阵容已确定（提交前预览），**当** 调用阵容平衡预览接口，**那么** 系统返回 A队/B队的平均 `conservative_rating` 及差值（平衡分），供管理员调整阵容。
3. **给定** 队员刚注册尚未参赛，**当** 请求个人面板，**那么** 返回初始值（mu=25, sigma=8.333），前端展示"暂无比赛数据"而不是报错。

### 用户故事 6 - 队员默契度（Chemistry）计算与排行 (优先级: P2)

系统根据两名队员共同赢球次数和得分-助攻组合出现次数，计算每对队员的默契度分值，并提供按默契度排序的配对排行榜（默契度榜）。

**优先级原因**: 默契度维度是赋予数据"社交价值"的亮点功能，强化队员之间互动感知；建立在基础评分和比赛数据之上，因此为 P2。

**独立测试**: 构造 3 场比赛数据（player_A 和 player_B 同队赢球 2 次，且有 3 次 A 得分 B 助攻的组合）→ 调用默契度计算接口 → player_A & player_B 的 chemistry_score 高于其他配对。

**验收场景**:

1. **给定** 两名队员有 ≥ 3 场共同参赛记录，**当** 请求默契度计算，**那么** 系统返回该配对的 `chemistry_score = chem_w1 * wins_together + chem_w2 * combo_count`，权重来自 TeamSettings。
2. **给定** 系统有多对队员的 chemistry_score，**当** 请求默契度榜，**那么** 按 chemistry_score 降序返回队员配对列表，每项显示：配对姓名、共同赢球场次、得分+助攻组合次数、总 chemistry_score。
3. **给定** 两名队员共同参赛场次 < 3，**当** 请求该配对的 chemistry_score，**那么** 系统返回 `{"chemistry_score": null, "reason": "数据不足（共同参赛场次 < 3）"}`，不参与默契度榜排行。
4. **给定** 一场比赛中 player_A 进球、player_B 助攻，以及另一分 player_B 进球、player_A 助攻，**当** 计算 combo_count，**那么** 两个方向均计入（combo_count += 2），体现双向配合。

### 边界情况

- 所有 μ 值在理论上无上下界，但 μ < 0 时记录 WARNING 日志（提示配置可能有问题）
- σ 有下界（通过引擎参数 `tau` 设置动态因子防止完全收敛），避免老队员评分完全固化
- 个人贡献 contribution_score 归一化：同队内按相对值调整，防止高进球场次对其他队员造成过大扭曲
- 算法系数变更不追溯历史比赛；评分历史中记录计算时使用的系数快照
- 外战仅有 1 名本队队员时（极端情况），仍正常计算，不拒绝

## 需求 *(必填)*

### 功能需求

- **FR-001**: 系统必须使用 `openskill` 库的 PlackettLuce 模型作为核心评分算法
- **FR-002**: 系统必须支持 Level 0-3 数据降级策略，不同等级使用不同的个人贡献权重计算路径
- **FR-003**: 外战必须使用对手强度映射虚拟对手 μ/σ，映射公式须在算法配置中可查
- **FR-004**: 个人贡献分公式须为：`contribution = beta * goals + gamma * assists + d_weight * max(0, plus_minus)`，系数来自队伍配置
- **FR-005**: 综合排名分须为：`composite = ts_weight * conservative_rating + perf_weight * avg_performance_score`，权重来自队伍配置
- **FR-006**: 所有算法系数必须从队伍配置表读取，引擎不得使用硬编码的全局常量
- **FR-007**: 队伍配置不存在时，引擎必须使用内置默认值正常运行（不报错）
- **FR-008**: 每次评分计算完成后，评分历史必须记录：μ 变化量、σ 变化量、数据等级、使用的系数快照
- **FR-009**: 引擎必须提供阵容平衡预览方法（接受两队队员列表，返回双方平均 conservative_rating 及差值，不写入数据库）
- **FR-010**: 管理员必须能够通过 API 修改算法系数，参数须经范围校验
- **FR-011**: 系统必须实现默契度（chemistry）算法：`chemistry = chem_w1 * wins_together + chem_w2 * combo_count`；仅共同参赛 ≥ 3 场的配对参与排行；结果按 chemistry_score 降序输出默契度榜

### 算法参数说明

| 参数 | 含义 | 默认值 | 有效范围 |
|------|------|--------|---------|
| `alpha` | 个人贡献调整幅度（相对于基础 OpenSkill 变化的放大/缩小） | 0.3 | [0, 1] |
| `beta` | 进球权重 | 0.6 | [0, 2] |
| `gamma` | 助攻权重 | 0.4 | [0, 2] |
| `d_disc_weight` | 防守盘权重 | 0.3 | [0, 2] |
| `composite_ts_weight` | 综合分中 OpenSkill conservative_rating 占比 | 0.85 | [0, 1] |
| `composite_perf_weight` | 综合分中近期表现分占比（两者之和须 ≤ 1） | 0.15 | [0, 1] |
| `chem_w1` | 默契度公式中"共同赢球"权重 | 1.0 | [0, 5] |
| `chem_w2` | 默契度公式中"得分+助攻组合"权重 | 2.0 | [0, 5] |

### 关键实体

- **队伍配置（TeamSettings）**: 存储本队所有算法系数，单队唯一记录，管理员可修改（含 alpha/beta/gamma/d_disc_weight/composite_ts_weight/composite_perf_weight/chem_w1/chem_w2）
- **评分历史（RatingHistory）**: 每次评分事件追加，包含 μ/σ 变化量、数据等级、使用系数快照（保证历史可审计）
- **默契度记录（ChemistryRecord）**: 以 (player_min_id, player_max_id) 为主键的配对记录，存储 wins_together、combo_count、chemistry_score；每次比赛提交后增量更新

## 成功标准 *(必填)*

### 可衡量的结果

- **SC-001**: 单场比赛（10 人）的评分计算时间不超过 1 秒（本地 NAS 环境）
- **SC-002**: 连续 100 场内战模拟数据测试后，初始相同评分的队员经过不同表现后，评分分布应有显著分化（标准差 > 初始 σ 的 20%）
- **SC-003**: 任意历史比赛的评分重算结果与首次计算结果一致（给定相同输入，输出 100% 幂等）
- **SC-004**: 管理员修改算法系数后，下一场比赛提交时使用新系数，旧比赛评分历史不受影响
